## Domain glossary

| **Term** | **Definition** | **Aliases to avoid** | 
| :--- | :--- | :--- |
| **Candidate** | A person using PrepBuddy to practise for an interview. | Applicant, user (when referring specifically to the interview participant) | 
| **Resume** | The candidate's career document containing evidence such as skills, experience, education, and projects. It is an input source for personalized questions. | CV, résumé file, profile document (use *Resume* for the domain concept) | 
| **Job Description (JD)** | The description of a particular job opening, including its responsibilities and required skills. When supplied, it helps tailor questions and identify skill gaps. | Job posting, vacancy text, job spec (use *JD* after first mention) | 
| **Target Role** | The kind of position the candidate is preparing for, such as Backend Engineer or Data Scientist. It provides role context when a resume is absent and may be inferred from supplied documents. | Role, job title, career path (use *Target Role* for the candidate's intended position) | 
| **Role Knowledge Base** | Curated role-specific knowledge used to ground questions when the interview is role-based rather than resume-based. | Question bank, role database, generic context (do not use these as exact synonyms) | 
| **Interview Setup** | The configuration step where the candidate chooses available source material, target role when needed, difficulty, and question count before starting. | Interview settings, session configuration (use *Interview Setup* for the candidate-facing step) | 
| **Interview Mode** | The source strategy that determines which evidence may be used to create interview questions: resume-based or role-based, with an optional JD where supported. | Interview type, source mode (use *Interview Mode* for the selected context strategy) | 
| **Interview Session** | One persisted mock-interview attempt, including its questions, submitted answers, evaluations, status, and report data. | Interview, session, attempt (use *Interview Session* for the domain entity; *session* is acceptable after context is established) | 
| **Interview Blueprint** | The planned sequence or coverage plan for an interview, including the objective of each turn, so the session progresses through different competencies instead of repeating a generic question pattern. | Question list, script, template (use *Interview Blueprint* for the plan, not the actual questions) | 
| **Turn** | One step in an interview's planned progression, associated with an objective such as debugging, architecture, or security. A turn is not itself an evaluation score. | Round, question number, stage (use *Turn* for a planned interview step) |
| **Interview Question** | A question generated for the current interview from permitted retrieved evidence and the current blueprint objective. | Prompt, query, item (use *Interview Question* for what the candidate is asked) | 
| **Candidate Answer** | The response submitted by the candidate to an interview question. It is the evidence evaluated for that turn. | Response, reply, submission (use *Candidate Answer* in domain discussions) | 
| **Answer Evaluation** | The assessment of a submitted candidate answer against the interview rubric. It produces dimension-level feedback and a score when evaluation succeeds. | Review, grading, interview evaluation (use *Answer Evaluation* for one answer; use *Interview Report* for the whole-session result) | 
| **Evaluation Rubric** | The five dimensions used to assess an answer: relevance, technical correctness, completeness, clarity, and depth. | Criteria, metrics, categories (use *Evaluation Rubric* for the complete five-dimension framework) | 
| **Dimension Score** | The score assigned to one rubric dimension for an evaluated answer. | Rating, category score, overall score (avoid *overall score* for a single dimension) | 
| **Answer Score** | The score for an individual answer, expressed on the evaluation scale. It can inform the next question's difficulty when the evaluation is valid. | Interview score, final score (reserve *Interview Score* for an aggregate result) | 
| **Interview Score** | An aggregate performance result for the interview session, distinct from any single answer score or dimension score. | Answer score, rubric score (use *Interview Score* only for the session-level result) |
| **Adaptive Difficulty** | The rule that adjusts the difficulty of a subsequent question in response to a valid answer evaluation. The documented thresholds are a score of at least 8.0 to step up and at most 4.5 to step down. | Dynamic level, automatic grading (use *Adaptive Difficulty* for the difficulty adjustment, not evaluation itself) | 
| **Retrieved Evidence** | Resume, JD, or role-knowledge content retrieved for the active interview mode and used to ground question generation or evaluation. | Context, data, documents (use *Retrieved Evidence* when referring to the actual retrieved supporting content) | | **Retrieval Scope** | The allowed source collection and metadata filters for a retrieval operation, including user and document boundaries where applicable. It prevents a question from using source material outside the active mode or candidate's permitted data. | Search scope, filter, context (use *Retrieval Scope* for the retrieval boundary, not the retrieved text) | 
| **Embedding** | A numerical vector representation of a document chunk or query, used to find semantically relevant content in the vector store. | Vector, feature array (use *Embedding* for the semantic representation; use *Vector* only when discussing the underlying data structure) | 
| **Document Chunk** | A section-sized piece of extracted resume or JD text stored and retrieved as a unit for semantic search. | Paragraph, fragment, segment (use *Document Chunk* for a unit created by the ingestion pipeline) | 
| **Skill Gap** | A difference between the skills expected by a supplied JD and the evidence available in the candidate's resume or answers. It is meaningful only when the relevant comparison source exists. | Weakness, missing skill, mismatch (use *Skill Gap* for a JD-relative difference; use *Weakness* for feedback about performance) | 
| **Strength** | A positive, evidence-based observation about the candidate's answer or interview performance. | High score, skill, advantage (use *Strength* for a feedback finding, not as a synonym for a score) | 
| **Weakness** | An evidence-based limitation in an answer or performance that the candidate can improve. | Skill gap, error, low score (use *Weakness* for performance feedback; use *Skill Gap* for JD-relative missing or weak coverage) | 
| **Interview Report** | The session-level summary produced after an interview, including aggregate score, rubric breakdown, strengths, weaknesses, and applicable JD skill-gap findings and suggestions. | Result, evaluation, summary (use *Interview Report* for the whole-session artifact) | 
| **Interview History** | The candidate's list of previously persisted interview sessions and their outcomes, used to revisit reports and review progress over time. | Dashboard, reports, session list (use *Interview History* for the collection of past attempts; *Dashboard* is a UI page) | 
| **Session Status** | The lifecycle state of an interview session, distinguishing an active/in-progress session from a completed one and any other explicitly represented state. | Progress, result, completion (use *Session Status* for lifecycle state, not the progress indicator) | 
| **User-Scoped Retrieval** | Retrieval restricted to data that belongs to the authenticated candidate, rather than searching another candidate's private resume or JD content. | Personal search, user filter, private context (use *User-Scoped Retrieval* for the ownership boundary) | 
## Flagged ambiguities

The following terms are easy to conflate across the project plan, UI, backend, and AI service. Use the preferred term in the final column consistently in documentation, API descriptions, prompts, and code comments.

| **Ambiguous wording** | **Concepts being confused** | **Preferred meaning / which one wins** |
| :--- | :--- | :--- |
| **Role** | The candidate's intended job position vs. the curated knowledge source for that position | Use **Target Role** for the position (e.g. Backend Engineer). Use **Role Knowledge Base** for the curated source of role-specific evidence. |
| **Role-based** | An interview mode vs. a role label or a knowledge-base collection | Use **Role-Based Interview Mode** only for the mode that retrieves from the Role Knowledge Base, optionally combined with a JD. |
| **JD / Job Description / job posting** | Three names for the same job-opening document | Use **Job Description (JD)** on first mention and **JD** thereafter. Do not call it a *role*; the role is the position, the JD is the specific opening's requirements. |
| **Resume / profile / candidate context** | The uploaded resume document vs. the candidate's overall profile assembled from multiple sources | Use **Resume** for the uploaded document. Use **Candidate Profile** only when referring to the broader candidate information assembled from resume, answers, or other supported inputs. Avoid *profile* as a casual synonym for the resume. |
| **Question / turn / objective** | The text presented to the candidate vs. the planned step vs. the competency the step should cover | Use **Interview Question** for the displayed question, **Turn** for the step in the sequence, and **Question Objective** for the intended competency or task. |
| **Interview / Interview Session / interview mode** | The overall product activity vs. one persisted attempt vs. the source-selection strategy | Use **Interview Session** for one persisted attempt, **Interview Mode** for resume-based or role-based context selection, and **interview preparation** for the broader activity. |
| **Answer evaluation / interview evaluation / report** | Scoring one submitted answer vs. aggregating results for the entire session vs. the final artifact | Use **Answer Evaluation** for one answer, **Interview Score** for the aggregate score, and **Interview Report** for the session-level artifact. |
| **Score** | A rubric-dimension score, an individual answer score, or an aggregate session score | Qualify it as **Dimension Score**, **Answer Score**, or **Interview Score**. Never use bare *score* where the level affects interpretation. |
| **Difficulty** | The difficulty chosen at setup vs. the difficulty assigned to a later question after adaptation | Use **Initial Difficulty** for the setup choice and **Question Difficulty** for the level assigned to a specific generated question. Use **Adaptive Difficulty** for the rule that changes it. |
| **Strength / weakness / skill gap** | Candidate-performance feedback vs. a missing or weak skill relative to a JD | Use **Strength** and **Weakness** for answer/performance findings. Use **Skill Gap** only for a comparison against JD requirements. |
| **Context / retrieved evidence / retrieval scope** | The text returned from search vs. the boundary that controls which sources may be searched | Use **Retrieved Evidence** for returned content and **Retrieval Scope** for permitted stores and metadata filters. *Context* may be used informally but should be qualified in technical explanations. |
| **Interview history / dashboard / report** | Past sessions as domain data vs. a UI page vs. one session's result | Use **Interview History** for past attempts, **Dashboard** for the interface, and **Interview Report** for one session's results. |
| **Session / session status / progress** | The persisted interview attempt vs. its lifecycle state vs. the candidate-facing count of completed questions | Use **Interview Session** for the attempt, **Session Status** for lifecycle state, and **Interview Progress** for the displayed progress indicator. |
| **Question generation / next question** | The AI workflow that creates a question vs. the question returned for the next turn | Use **Question Generation** for the process and **Next Interview Question** for the result requested by the interview flow. |
| **Vector / embedding / document chunk** | The numeric representation vs. the semantic encoding process/result vs. the text unit being encoded | Use **Document Chunk** for source text, **Embedding** for its numerical semantic representation, and **Vector** only for the underlying numeric structure. |
| **User / candidate** | An authenticated application account vs. the person participating in an interview | Use **User** for authentication, ownership, and access-control concerns. Use **Candidate** for interview-domain behaviour and feedback. They may refer to the same person but are not interchangeable in every context. |

## Naming rules to keep

1. Prefer domain language over implementation language. Names such as *controller*, *handler*, *service*, *hook*, and *utility* describe code structure, not PrepBuddy's domain.
2. Do not describe PrepBuddy as using a static question list as its primary interview model. Questions are generated through a structured interview workflow and grounded in the evidence permitted for the active mode.
3. Never treat the Target Role, Resume, and JD as synonyms. They answer different questions: what position the candidate wants, what the candidate has done, and what a particular opening requires.
4. Keep answer-level evaluation separate from session-level reporting. A pending, failed, or missing evaluation must not be described as a completed score.
5. Apply user ownership and retrieval-source restrictions whenever discussing resume/JD retrieval; retrieved evidence must belong to the authenticated candidate and be allowed by the active Interview Mode.
